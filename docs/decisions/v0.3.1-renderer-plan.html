Why _x_ is on the ship list, against the handoff's advice

The handoff rejected underscore emphasis on the strength of a corpus scan naming rests_on, governed_by, claims_dir, schema_version, build_role, raw_html, migrated_from, validated_at, depended_by as everyday prose tokens. Re-running that scan confirms they are ubiquitous (governed_by 148 hits, rests_on 98, claims_dir 61, schema_version 60) — and confirms every one of them is intraword. CommonMark's flanking rule makes a _ with alphanumerics on both sides incapable of opening or closing emphasis, so not one of the nine cited tokens can misfire. The evidence the rejection rested on does not support it.

The residual exposure is word-boundary underscores only — leading-underscore identifiers, and a trailing underscore before punctuation. In this repo that is dominated by target="_blank" inside raw-html mockup fixtures, which never reach markdown.Render. Backslash escapes cover the rest, and markdown-sanity (D5) reports an unmatched run rather than letting it fail silently.

Rejecting also has a cost the handoff did not price: this repo's own markdown already uses _should_, _required_, _only_, _major_. People write it from muscle memory. A renderer that silently drops it is worse documentation, which is the thing this release exists to fix.

03Decided — the constructs the handoff ruled out

Each was rejected for a reason that holds when a claim is a bare assertion and weakens when a claim is documentation. The documentation goal moves all four. All decided 2026-07-29 — every one ships. The reasoning is kept below so the constraints survive into implementation.

D1 · DECIDED Headings — ### and deeper

Ships capped at ###. # and ## stay reserved for viewer chrome, so a body can never outrank the section heading above it, and the viewer's nav continues to ignore body headings entirely — one nav, one source.

The original objection is real: a claim already carries an id, a section (rendered as an in-content heading marker by sectionHeadingHTML, render.go:864) and its module tab, so body headings create a second outline the viewer's nav knows nothing about. But "if a body needs headings, it is two claims" is only true when a claim is one assertion. A documentation claim explaining a protocol has internal structure that is not two claims. Capping at ### keeps one nav-visible outline while letting a long body be readable.

D2 · DECIDED GFM pipe tables

Ships. layout: table remains the structured, linted option for a claim whose content is tabular data; pipe tables serve a documentation body that wants one small comparison table mid-prose. The two do not compete for the same job.

The objection was that a markdown table is the same data with none of the guarantees layout: table gives — rows-shape linting and model.RowColumns ordering. True — which is why layout: table keeps its role rather than being superseded. A documentation body that wants one small comparison table mid-prose cannot use it at all today, and splitting the claim to get one is the tail wagging the dog. Cost is real though — pipe tables need a cell-level inline pass, alignment row parsing, and escape handling for a literal |, which is why | joins the escapable set in §2. This is the largest single item on the page.

D3 · DECIDED Images ![alt](src) — shipping in claim bodies

Settled 2026-07-29: claim bodies get image support. The handoff's non-goal is overturned — layout: mockup stays the reviewed path for hand-authored HTML, but a documentation body that needs a diagram no longer has to become a mockup claim to get one.

How it ships

The handoff's objection here was the only security argument among the four, so the mechanism matters more than for D1/D2/D4. layout: mockup gates visuals behind three things: raw-html-scope's relative-only URL check (mockupAbsoluteURLPattern, which also normalizes control-character scheme evasion such as ht\ttp://host before deciding a value is relative), the raw_html_reviewed flag, and a module allowlist. A markdown image routes around all three unless it is explicitly wired to the first.

So: src goes through the same relative-only check, reusing raw-html-scope's existing implementation rather than a second copy of it. That keeps a claim body's image same-repo, which is also what makes the rendered viewer portable — an absolute src would make the artifact depend on a host staying up. alt text runs the inline pass and is escaped in attribute context. A rejected src renders as escaped literal text, never a broken <img>, and markdown-sanity (D5) reports it rather than letting it fail silently.

Comment bodies do not get images. They share this renderer (comments.html:18) but not the threat model: a comment is reviewer-authored, and an image reference in reviewer-authored text is a read receipt and an IP-address disclosure — who reviewed what, and when. Relative-only already blocks the remote-fetch path, so this is belt-and-braces rather than the load-bearing control, and it costs a reviewer nothing: a comment arguing about a diagram can link to it.

Mechanically this makes the image construct the first per-surface divergence in the renderer — every other construct behaves identically wherever it appears. So it needs a render option threaded from the caller rather than a global, and a test asserting that the same body text yields an <img> through the claim path and escaped literal text through the comment path. Parity landmine L5 gets a carve-out documented at exactly one place.

D4 · DECIDED Task-list items - [ ]

Ships, rendered as a disabled checkbox.

The objection stands on its own terms and does not survive the documentation goal: a locked claim documenting a migration checklist or a compatibility matrix is describing state, not asserting completion. Nearly free once list nesting is reworked. Rendered disabled, so nobody mistakes the viewer for a task tracker — the viewer is a review surface, and state changes belong in the claim text where the lock ledger can see them.

04Decided — not about constructs

D5 · DECIDED The new markdown-sanity lint ships in this release

This started as two problems. One of them is gone: the corpus is a handful of locked claims in a single project, and you have said you will unlock and revisit them against the new guidelines. So the "locked claims silently re-render after upgrade" problem needs no mechanism at all — a changelog note and your unlock pass cover it, and the one-time escaping migration that was on the table is dead. Good: it was the option that would have had dossierx migrate editing locked claim text, which is exactly what the v0.3.0 ledger exists to prevent.

What remains stands on its own: every degradation in this renderer is currently silent. An unclosed fence falls through as prose, an unclosed backtick renders literally, and a javascript: link renders as inert text with no warning at all — a security downgrade nobody is told about. After this release that surface roughly triples, and it grows a new class: an <img> whose src was rejected, a pipe table whose alignment row does not match its header, an unmatched underscore run.

Findings: unclosed fence · unclosed code span · unmatched emphasis/strike/underscore run · rejected link scheme · rejected image src · image in a comment body · malformed pipe table · dangling backslash · unresolvable list indentation.

Deferring to v0.3.2 was defensible — with a corpus this small you would find these by looking. What decided it is that the lint is what makes the ceiling knowable to the agent operating the CLI, which is the whole v0.3.0 thesis: an agent authoring a claim body gets told it wrote something the renderer will quietly drop, instead of the drop surfacing when a human happens to read the viewer. The lint is also cheapest to write while the parser is fresh — most findings are a by-product of state the parser already tracks.

THE SHAPE CONSTRAINT Most of this cannot be parallelised, and pretending otherwise costs more than it saves

internal/render/markdown/markdown.go is a single 507-line file, and P1 through P9 all rewrite it — the inline parser, the block scanner and the fence pass are three regions of one artifact, not three modules. Running them as concurrent agents in separate worktrees produces overlapping rewrites of the same functions, and the merge is a second implementation job done with less context than either original. The speed-up is negative.

So the pipeline is honest about it: one critical path with one owner at a time, and parallelism drawn only from files nothing else touches — the new lint package, style.css, components.go, and the docs. Those four lanes have no code dependency on the critical path, because the constructs are already fully specified on this page. They can start at T0 and integrate at gate 2.

CORRECTED Why these models — and why Fable 5 is not among them

The first version of this page put Fable 5 on the mechanical phases (P2–P5, CSS, docs) and Opus 5 on the hard ones. That was inverted, and worth stating plainly rather than quietly fixing:

ModelInput / output per MTokWhat it is for
Fable 5$10 / $50The most capable widely released model — the most demanding reasoning and long-horizon agentic work. 2× Opus 5's price.
Opus 5$5 / $25Complex agentic coding and enterprise work; strongest on deep reasoning and long-horizon execution.
Sonnet 5$3 / $15 ($2/$10 intro to 2026-08-31)Near-Opus quality on coding and agentic work at Sonnet cost.
Haiku 4.5$1 / $5Fastest and cheapest; simple, well-bounded tasks.

Putting the most expensive model on seven transcription-shaped nodes while the cheaper model did the parser rewrite is backwards on both axes at once. Corrected assignment, by one rule — match the model to how much of the work is judgment rather than transcription:

  • Opus 5 — P1, P6, P7, P8, P10, the security verifiers, the integration read. These are the phases where the design is not fully determined by the spec, or where a mistake is silent and security-relevant.
  • Sonnet 5 — P2–P5, CSS, components, docs, and the diff reviewers. Every one of these has its design already settled on this page; what remains is faithful construction, which is exactly where Sonnet 5 now sits close to Opus.
  • Haiku 4.5 — P0 and P9. Capture and emit, no judgment.
  • Fable 5 — the six security verifiers, and nothing else. Not the implementation phases: those arrive with their constraints written down, so the top tier buys latency and cost rather than correctness there.

Where Fable 5 does earn its 2×

Every implementation phase on this page is a closed problem: the construct, the ceiling, the degradation rule and the landmine are all written down before the agent starts. Adding capability above Opus 5 there mostly buys deliberation on a question that is already answered.

The adversarial security verify is the opposite shape. "Is there a way this escaping boundary breaks that nobody has thought of" is genuinely open-ended — the verifier is not checking work against a spec, it is trying to find the case the spec does not cover. That is the one question on this page where the capability ceiling maps directly onto whether the answer is right, and where being wrong is silent: a hole in renderInline or in the image src gate does not fail a test, it just sits there.

It is also where the premium is cheapest. The verifiers are read-only and low-output — they read a diff and return a verdict, they do not write code. Paying $50 per MTok of output on six short verdicts is a small absolute cost; paying it on seven implementation phases that emit a parser, a stylesheet and a docs pass was not. So: Fable 5 on the six verifiers, Opus 5 on the hard implementation, Sonnet 5 on the specified construction, Haiku 4.5 on capture. If you would rather keep the verifiers on Opus 5, that is defensible too — it is a judgment call about how much the last increment of adversarial reach is worth, not a correctness question.

Two Opus 5 behaviors worth knowing, since they shape the review workflow below: it verifies its own work unprompted (so "add a verification step" instructions are now counterproductive — the phase prompts must not carry them), and it delegates to subagents readily (so the phase prompts cap spawning rather than encouraging it). Neither changes the case for the independent security verifiers in §6 — self-verification and adversarial verification by an agent that did not write the code are different things, and only the second catches a blind spot the author shares with themselves.

Four settings that ride along with effort

  • max_tokens ≥ 64K on every xhigh / max node. Effort raises how much the model thinks, and max_tokens caps thinking plus response together — size it too tightly and the phase truncates mid-answer with stop_reason: "max_tokens".

The four human checkpoints

  • Gate 0 — before any code exists. C6's spec deltas: concrete proposed amendments to this page, ranked by what they would have cost to discover during the build. You accept or reject each one. This is the only checkpoint where changing your mind is free.
  • Gate 1 — after P1, before anything is built on it. The parser contract: the escapable set, what happens inside a code span, and the exact fall-through behaviour on malformed input. Everything downstream inherits these, so this is the cheapest possible place to disagree.
  • Gate 2 — after P9 and lane integration. A lavish page rendering every construct before and after, from real claim bodies. This is where "does documentation actually read better now" gets answered, which is the release's whole premise.
  • Gate 3 — before the tag. The release checklist in §9, the full diff, and the changelog wording on locked-body re-render.

Between gates, agents merge on green tests plus a clean review — no human ack per phase. That is the trade that makes the run worth orchestrating: you review three artifacts closely instead of fourteen diffs shallowly.

  • Your review time at the four gates. Gate 2 in particular is "read rendered before/after samples for every construct and decide whether documentation actually reads better" — that is a sitting-down task, not a glance, and it is not in the 5–8 hours.
  • Fix-loop iterations are the dominant variance. Every number above assumes each phase passes review and verification on the first pass. A phase that fails its golden diff and goes back around roughly doubles. If P1's escaping boundary needs two rounds, everything downstream shifts.
  • Elapsed time is not agent time. Between-gate stretches run unattended, but the run pauses at each gate until you look. Realistically this is two to three working sessions, not one continuous block.
  • Long single turns are expected, not a hang. A high-effort agent on a hard node can sit for many minutes without emitting anything. Don't kill it.

TOKEN DISCIPLINE What this shape deliberately avoids

  • No discovery agents. The scope, the phase list, the file ownership and the model per node are all fixed on this page. Nothing in the run decides what the run contains.
  • No loop-until-dry. Every stage has a counted agent list. The only repetition is a fix-and-retest cycle inside a phase, bounded by its own tests.
  • Goldens captured once. P0 runs a single time; every later phase diffs against that artifact instead of re-deriving a baseline.
  • Reviewers read diffs, not repositories. A reviewer that has to locate the change first spends most of its budget on orientation.
  • No worktree isolation on the critical path. Worktrees cost setup and disk per agent and only pay when agents write concurrently — which, per the shape constraint above, these do not.
