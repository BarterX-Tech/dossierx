# DossierX v0.4.1 — design

Date: 2026-08-03
Branch: `v0.4.1`
Version: patch bump to **v0.4.1** (see Q5)

Two work items ship together as one release.

1. **BLOCKER — github issue #25.** `raw_html` becomes an *attachment* a claim may
   carry on any layout, not a layout of its own.
2. **UI — approved viewer redesign.** The shared edges footer collapses into a
   native `<details>`; the comment chip moves out of that footer and into the
   card head.

They ship together because they touch the same six layout partials in the same
place. Splitting them means editing `card.html` / `table.html` / `list.html` /
`steps.html` / `tree.html` / `mockup.html` twice and reconciling two rounds of
hand-written string-literal test churn against the same lines.

---

## 1. `raw_html` becomes an attachment (issue #25)

### 1.1 What is wrong today

`raw_html` is legal **only** on `layout: mockup`. That conflates two unrelated
things:

- *where* the blob may sit in a claim (a layout question), and
- *who* may author it and *what* markup may get through unescaped (a security
  question).

A claim that is genuinely a table, or a list of steps, cannot carry a diagram
or a small rendered mockup alongside its rows. Authors work around it by
splitting one fact across two claims, which is exactly the duplication the
project's single-source-of-truth rule exists to rule out.

### 1.2 The change, stated narrowly

`internal/lint/raw_html_scope.go`, `checkMockupGate`, **leg 1 only**:

```go
// 1. Layout gate.
if c.Layout != model.LayoutMockup {
    mockupFinding(fmt.Sprintf("raw_html is only legal on layout: mockup, got layout: %q", c.Layout))
}
```

This check is deleted. A claim may carry `raw_html` alongside `body` / `rows` /
`steps` on **any** of the seven layouts. `layout: mockup` stays a valid,
first-class layout and keeps its current meaning (a claim whose *primary*
content is the blob).

`checkMockupGate`'s five legs are five independent `mockupFinding(...)` calls
with no shared boolean and no early return between them. Deleting leg 1
provably cannot perturb legs 2–5.

### 1.3 What explicitly does **not** change

| Surface | Status | Why |
|---|---|---|
| Leg 2 — `cfg.MockupModules` module allowlist | **unchanged** | Governs *who* may author unescaped markup. Orthogonal to *where* it sits. |
| Legs 3 & 4 — `checkMockupMarkup` tag/attr/class allowlist (`div`/`span`/`b`/`br`/`img`, `gcp-*`/`mockup-*` classes, relative-only `src`) | **unchanged, does not widen** | Already layout-blind: `checkMockupGate` guards it only on `c.RawHTML != ""`. It has always fired identically for any layout. |
| Leg 5 — `RawHTMLReviewed` lock-lifecycle gate | **unchanged** | A human still signs the markup before the claim can lock. |
| `components.MockupHTML` render-time gate | **unchanged — see decision C2** | |
| `internal/serve`'s `disarmUngatedMockups` | **no edit** | It calls `lint.MockupGateFindings`, which calls the same `checkMockupGate`. It inherits the relaxation automatically; legs 2–5 remain the real defense. |
| `Claim.ContentHash` exclusion of `raw_html` / `raw_html_reviewed` | **unchanged** | Keyed off the field name, never off layout. |
| `internal/lint/layout_shape_mismatch.go` | **unchanged** | Already treats `RawHTML` as content-bearing on any layout, and defers the mockup constraint to `raw-html-scope` in its own comment. |

**The security boundary does not move.** This change alters *where* `raw_html`
may sit. It never alters *who* may author it, nor *what* markup gets through
unescaped.

### 1.4 Render position

`raw_html` renders **after the claim's own main content, before the edges
footer** — the position `mockup.html` already uses today, applied uniformly.

Emitted markup, identical on every layout that gets it:

```html
<div class="claim-mockup-body">…MockupHTML(claim, allowlist) output…</div>
```

**Decision D2 — the wrapper class stays `claim-mockup-body` on all layouts.**
Not a new `claim-raw-html`. Reasons: (a) `mockup.html`'s emitted bytes then do
not change at all for this work item; (b) the existing `.claim-mockup-body`,
`.gcp-*` and `.mockup-*` rules in `style.css` and any project's own mockup CSS
keep working unmodified; (c) a second wrapper class would need a parallel copy
of every one of those rules. The class name now reads as "the raw-HTML body
wrapper", which is what it always was.

Per-layout insertion points:

| Layout | Inserted after | Inserted before |
|---|---|---|
| `card` | `.claim-body` / `No body.` | `{{edges .}}` |
| `table` | `.claim-table-scroll` / `No rows.` | `{{edges .}}` |
| `list` | `.claim-list-items` / `No items.` | `{{edges .}}` |
| `steps` | the last `.step` bubble / `No steps.` | `{{edges .}}` |
| `tree` | `pre.claim-tree-body` / `No tree content.` | `{{edges .}}` |
| `mockup` | `.claim-body` | `{{edges .}}` (already correct — no change) |
| `banner` | `.claim-body` / `No body.` | `</section>` (banner has no footer) |

No new template-func plumbing is required. `attachMockupOverride` already
rebinds `mockupHTML` on **every** partial in the map, and `Render` calls it
unconditionally, so the func is live in every partial's scope today — only
`mockup.html` happens to call it. Each remaining partial needs one line.

### 1.5 Stale prose that must be corrected with the code

These read as enforcement statements and become false the moment leg 1 goes:

- `FORMAT.md:28` — `raw_html: string  # optional, layout: mockup only (review-gated)`
- `FORMAT.md:74-77` — the layout-inference paragraph
- `internal/model/claim.go:280` — "RawHTML is a project-authored blob of raw HTML **for layout: mockup** claims"
- `internal/lint/raw_html_scope.go:15` and its numbered point 1 in the package doc
- `internal/render/components/mockup.html:11-13` — "layout is exactly mockup (so RawHTML **can never be smuggled into a card/table/list/steps/banner body**)"
- `README.md:304` — the config-schema row calling `mockup_modules` "the allowlist of modules permitted to author **`layout: mockup` claims**". The allowlist is keyed on `raw_html`, never on layout; that row is true only while leg 1 holds. It is the field's only prose description in the repo, and no test pins it.

The last one is the most dangerous to leave: it tells a future reader that a
guarantee exists which this release deliberately removes.

## 2. Viewer redesign

### 2a. The edges footer moves inside a native `<details>`

Today every non-banner partial ends with a flat
`<ul class="claim-edges">…</ul>` built by
`components.EdgesHTMLWithLinks`, followed (when the claim has threads) by the
baked comments panel.

**New shape.** The `<ul>` is **relocated, not rewritten** — byte-identical
where possible. Only its container changes.

```html
<details class="claim-links" open><summary class="claim-links-summary">4 links - 2 files - 1 drifted</summary><ul class="claim-edges"><li class="claim-governed">governed_by: <a href="#doctrine.hub.retries">Doctrine › Retries</a></li><li class="claim-rests-on">rests_on:<ul class="claim-edge-id-list"><li>…</li></ul></li><li class="claim-review-pending">review_pending</li><li class="claim-implemented-in">implemented in: <code>internal/http/retry.go#Do</code> <span class="pill pw">drifted</span></li></ul></details><div class="comments-panel" data-claim-id="widget.contract.retry-policy">…</div>
```

Every `<li>`, every `writeClaimRef` / `writeIDListItems` byte, and the
`.pill.pw` drifted marker are unchanged. The one removed `<li>` is the comment
chip (see 2b).

#### Summary line — exact count rules

One mono line, three terms, emitted in this order and joined by `-`
(settled: **C7**, **C8**):

- **links** = the number of *individual claim ids* the reader will find on
  expanding, not the number of `<li>` lines. Concretely: `governed_by`,
  `migrated_from` and `review_pending` contribute **one each** when present
  (they carry at most one target); `mirrors`, `rests_on` and `depended on by`
  contribute **one per id** inside each list (so `rests_on` with two ids
  contributes 2, not 1). Example (C8): `governed_by` + `mirrors` (1 id) +
  `rests_on` (2 ids) + `depended_on_by` (2 ids) = 6 links.
- **files** = `len(files)` — one per `li.claim-implemented-in`.
- **drifted** = the number of those files with `ViewFile.Drifted == true`.

Rendering rules (C7):

- **links** and **files** are always emitted, even when their count is `0`,
  whenever the `<details>` itself is emitted at all (see the zero-edge
  suppression rule below for when the whole thing is omitted instead).
- **drifted** is the one term suppressed by count: it is emitted only when
  it is **> 0**. Drift is the one thing a collapsed footer must never hide,
  so it earns its own segment exactly when there is something to hide.

Worked examples:

| Footer content | Summary |
|---|---|
| governed_by + mirrors (1 id) + rests_on (2 ids) + depended_on_by (2 ids), 0 files, no drift | `6 links - 0 files` |
| governed_by + rests_on (3 ids), 1 file, no drift | `4 links - 1 files` |
| governed_by + rests_on (3 ids), 2 files, 1 drifted | `4 links - 2 files - 1 drifted` |
| only `migrated_from` | `1 links - 0 files` |
| only 2 implemented-in files | `0 links - 2 files` |
| nothing | *(no `<details>` emitted)* |

Pluralisation is deliberately not done — `1 links` is accepted. It keeps the
line a fixed mono shape that scans as a column across a page of cards, and
keeps the emitter a single `fmt.Sprintf`. This, the link-counting rule and the
separator were the open question **Q1**; all three are now settled by **C7**
and **C8** and Q1 is closed (see §5).

#### Zero-edge suppression

A claim with zero edges *and* zero linked files emits **no `<details>`, no
`<summary>` and no `<ul>`** — not an empty disclosure triangle labelled "0".

This is the assertion that flips
`TestEdgesHTML_MinimalClaimOmitsFacetModuleAndEmptyFields`, which today expects
the bare `<ul>` wrapper to survive on a minimal claim.

The comments panel is **not** suppressed by this rule. It is a sibling emitted
independently of the `<details>` (see C5), so a claim with threads but no edges
still bakes its panel.

#### The three auto-open signals

Only **two** of the three signals are attributes the server writes into the
emitted bytes. The third — the deep-link target — cannot be, and is a CSS-only
mechanism instead (settled: **C9**, formerly decision D1 below):

1. **Any linked file is `Drifted`.** *(server-written)* Drift is the one fact
   in the footer that is actionable *now*; a collapsed footer that hides it
   defeats the point of computing it.
2. **The claim is `locked` and `review_pending`.** *(server-written)* Same
   reasoning: the footer carries `li.claim-review-pending`, the marker that
   this claim is waiting on a human.
3. **The card is the deep-link target.** *(CSS `:target`, not an attribute,
   not JS)* — see decision **D1** below.

Both server-computed signals are already in scope inside
`EdgesHTMLWithLinks(c, files, dependedBy, targetStatuses)`: drift comes off the
`files` slice, review-pending off the claim. **The function signature does not
change**, and `attachEdgesOverride` needs no new argument.

#### Decision D1 — the deep-link signal is CSS `:target`, not an attribute (C9)

A URL fragment is not knowable at render time. Nothing in `internal/render` or
`internal/serve` sees the hash; `shell.html` reads `window.location.hash`
client-side (lines 237, 254). There is no server-side path by which "this card
is the deep-link target" could become an `open=""` in the emitted bytes — the
original design was impossible as written.

Resolution, per **C9**: a CSS rule, not a server-written attribute and not
JavaScript —

```css
.claim:target .claim-links > *:not(summary) { content-visibility: visible; }
```

— renders `details.claim-links` open via CSS alone inside the `:target`
section, so it survives the static `file://` export. No JavaScript, no
attribute mutation, and it targets exactly the canonical copy —
`stripOverviewIDs` removes `id=` from every non-canonical overview copy, so
only one element on the page can ever match `:target`.

This is recorded as a design decision rather than an omission because the
approved sketch said "the server writes the open attribute"; for this third
signal it provably cannot, and the substitute is stated here rather than
discovered during implementation. This substitution is now settled (C9), not
open. The fallback, if the CSS proves unreliable in a target browser, is one
line in `shell.html`'s **existing** hash handler setting `.open = true` —
which the chromedp suite can prove — but the primary mechanism is CSS-only.

### 2b. The comment chip moves into the card head

Today the chip is an `<li class="claim-comments">` emitted *inside* the edges
`<ul>` by `EdgesHTMLWithLinks`. Once the footer collapses, the chip would be
hidden behind a closed disclosure — the control for opening a comment thread
would itself need a click to reveal.

**New shape.** The chip becomes a standalone emitter (`commentChip` template
func over `components.CommentChipHTML(c)`), called from each partial's `.k`
head line.

Before:

```html
<div class="k" data-claim-id="widget.contract.retry-policy" title="widget.contract.retry-policy">Retry Policy <span class="pill ps">locked</span></div>
```

After:

```html
<div class="k" data-claim-id="widget.contract.retry-policy" title="widget.contract.retry-policy"><span class="label">Retry Policy <span class="pill ps">locked</span></span><span class="claim-comments-slot" hidden><button type="button" class="comment-chip comment-chip--empty" data-claim-id="widget.contract.retry-policy" aria-controls="commentsPanel" aria-expanded="false" aria-label="add the first comment on this claim"><span class="comment-chip-glyph" aria-hidden="true">💬</span> <span class="comment-chip-count">0</span></button></span></div>
```

Invariants, all preserved from today:

- **Same button.** Same `type`, same `comment-chip` classes, same three
  variants (`--open` / `--resolved` / `--empty`), same `data-claim-id`, same
  `aria-controls="commentsPanel"`, same `aria-expanded`, same `aria-label`
  strings, same glyph + count spans. `updateChips` rewrites all of them
  unchanged.
- **Same `hidden` migration.** The `hidden` attribute that today ships on
  `<li class="claim-comments">` and is stripped by `shell.html`'s
  `syncEmptyChips` after the `/api/ping` probe now ships on
  `<span class="claim-comments-slot">`. `closest('.claim-comments')` becomes
  `closest('.claim-comments-slot')` in `updateChips` and `syncEmptyChips`.
- **No `id=` anywhere.** Overview claims render N times; state fans out by
  `data-claim-id` + `querySelectorAll`, never `getElementById`. Nothing in the
  new markup adds a ` id="` sequence, so `stripOverviewIDs`' leading-space
  literal match still hits exactly the root `<section>` attribute.
- **Hand-escaping.** `CommentChipHTML` returns `template.HTML` from a FuncMap,
  which bypasses `html/template` auto-escaping, so `c.ID` and the label go
  through `html.EscapeString` exactly as they do in `EdgesHTMLWithLinks` today.

#### `.k` becomes a flex row

```css
.k { display: flex; align-items: baseline; gap: 8px; /* existing font/size/color/margin kept */ }
.k > .label { flex: 1 1 auto; min-width: 0; }
.k > .claim-comments-slot { margin-left: auto; flex: 0 0 auto; }
```

`.label` holds the label text **and** the status pill and flexes; the slot is
pushed right by `margin-left: auto`.

**`banner.html` keeps its flat `.k` line unchanged** — no `<span class="label">`
wrapper, no slot, no flex. It gets no chip (C3/C6), so there is nothing to push
right and no reason to change its emitted bytes. This matters for the test
rewrite: `TestPartialHeadings_LabelIDAndKeepMachineIDReachable` iterates all
seven layouts, and banner's subtest must keep expecting the **old** prefix while
the other six expect the new one.

#### Hover-reveal contract for the zero-comment chip

The empty chip is dimmed at rest and revealed on card hover/focus. It is
**never `display: none`** — it must stay in the tab order so a keyboard user
can open the first comment on a quiet claim.

| State | opacity |
|---|---|
| at rest | `0` |
| card `:hover` or `:focus-within` | `.75` |
| the chip itself `:hover` / `:focus-visible` | `1` (plus today's solid accent border, `--ink` text) |

This replaces today's flat `opacity: .75` at rest on `.comment-chip--empty`.

`[hidden]` (the static-`file://` case, where no comment API is reachable) still
hides the slot outright — that is a *capability* signal, not a *noise-floor*
one, and it applies to the slot, not the button.

**tree.html renders without the `.card` class.** Every hover-reveal, `.k`-flex
and print rule therefore needs a `.claim-tree`-scoped duplicate, following the
existing `.card.claim-card--commented, .claim-tree.claim-card--commented`
precedent at `style.css:779-782`. A `.card`-scoped rule silently no-ops on tree
claims — it will not fail a test, it will just quietly not work.

#### Obsolete CSS

`.claim-comments { list-style: none; }` (style.css:721) exists only because the
chip was an `<li>`. It goes.

## 4. Settled decisions

These were raised as blocking questions and answered by the human after the
scout pass. They are recorded here so they are not re-litigated.

### C1 — the layout gate lives in `internal/lint`, not `internal/check`

The rule to relax is `checkMockupGate`'s point-1 layout check in
`internal/lint/raw_html_scope.go` (around lines 226-229).
`internal/check/check.go` only calls `lint.RunAll`; it defines no raw-html-scope
logic of its own. The lint file is the target.

### C2 — `components.MockupHTML` is left **exactly** as it is

```go
trusted := c.Status == model.StatusLocked && c.RawHTMLReviewed && stringInSlice(allowlist, c.Module)
```

This render-time gate has **no layout term and never had one**. The layout
constraint has only ever lived in the lint.

**Decision: do not add a defensive layout check here.** It is tempting — a
second layer that also asserts `layout == mockup` reads like defense in depth.
It is not. It would re-encode layout scope in a second place, which is the
exact duplication issue #25 exists to remove, and it would silently break every
newly-legal card/table/list/steps/tree/banner claim carrying `raw_html` — the
feature would compile, lint clean, and render escaped-as-text with no error
anywhere.

`MockupHTML` remains the real second layer for the questions that *are* its
business: is the claim locked, was the markup reviewed, is the module
allowlisted. Those are unchanged.

This is recorded as a deliberate choice, with reasoning, rather than left as an
omission for a reviewer to wonder about. An inline comment in `components.go`
states the same thing at the code, so the next person to reach for a defensive
`if c.Layout != …` finds the answer where they are standing.

### C3 — `banner.html` gets `raw_html`

The #25 ask is literally "any layout". Banner is one of the seven. It gets the
attachment block. Banner's exclusion from the *UI* work is structural — it has
never called `{{edges .}}` — and has nothing to do with `raw_html`. So: banner
gets the attachment, and still gets no edges footer and no comment chip.

### C4 — `build_order.html` is out of scope for both items

Its hand-built `div.claim-edges` is not wrapped in `<details>` and it gets no
chip. It renders one module's locked build-order artifact and is not keyed by
`claim.Layout` at all. Zero edits.

### C5 — the comments panel stays **outside** the `<details>`

`commentsPanelTmpl`'s output remains a sibling emitted immediately after
`</details>`, keeping today's position relative to the enclosing `<section>`.

Rationale: the chip now lives in the card head. Putting the panel inside a
collapsed `<details>` would mean opening a comment thread requires first
expanding the footer — control and target in different places — and the viewer
JS does not expect that coupling. The panel is also emitted independently of
the zero-edge suppression rule, so a claim with threads but no edges still
bakes its panel with no `<details>` above it.

### C6 — the six partials that gain the chip slot

`card.html`, `table.html`, `steps.html`, `list.html`, `tree.html`,
`mockup.html`. `banner.html` and `build_order.html` get none. `tree.html`
renders without the `.card` class, so hover/reveal CSS must be scoped to reach
tree claims too.

### C7 — the summary line is three counts, drift-conditional only

`"N links - N files - N drifted"`. `links` and `files` are always emitted,
even at `0`, whenever the `<details>` itself is emitted. `drifted` is the one
segment suppressed when its count is `0` — drift is the one thing a collapsed
footer must never hide, so it earns its own segment exactly when there is one.
Separator is `-`. This settles (and closes) former **Q1**. See 2a above.

### C8 — "N links" counts individual claim ids, not footer lines

`governed_by`, `migrated_from` and `review_pending` contribute one each (they
carry at most one target); `mirrors`, `rests_on` and `depended on by`
contribute one per id inside each list. Example: `governed_by` (1) +
`mirrors` (1 id) + `rests_on` (2 ids) + `depended_on_by` (2 ids) = 6 links. It
counts what the reader will actually find on expanding. See 2a above.

### C9 — the deep-link auto-open signal is CSS `:target`, not a server attribute or JS

A URL fragment is never sent to the server and is unknowable at render time —
the original design was impossible as written. `details.claim-links` inside a
`:target` section renders open via CSS alone, so it survives the static
`file://` export. The other two auto-open signals (a drifted file,
locked + `review_pending`) **are** still server-written `open` attributes.
This is the same resolution recorded as decision **D1** below; C9 is the
human's settling of it as fact, not merely a flagged non-blocking scout note.

### D1 — deep-link auto-open is CSS `:target` (settled as C9)

See 2a above and **C9**.

### D2 — the raw_html wrapper class stays `claim-mockup-body`

See 1.4 above.

## 6. Non-goals

- Widening `mockup_modules`, the tag/attribute/class allowlist, or the
  `raw_html_reviewed` gate. None of these move.
- Any change to `internal/check`, `internal/config`, `internal/lock`,
  `internal/buildorder`, `internal/implink`, or
  `internal/lint/layout_shape_mismatch.go`.
- Any change to `build_order.html`.
- Any change to `EdgesHTMLWithLinks`' signature or to
  `attachEdgesOverride` / `attachMockupOverride`'s wiring (doc comments in
  `depended_by_view.go` do change, because they currently describe the chip as
  riding the edges footer).
- Regenerating any golden file. There is exactly one regeneration mechanism in
  this repo and it reaches none of the assertions this release churns — see the
  plan's golden-regeneration section.
