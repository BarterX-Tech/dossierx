# DossierX v0.4.1 — implementation plan

Date: 2026-08-03
Branch: `v0.4.1`
Design: [`docs/superpowers/specs/2026-08-03-v0.4.1-design.md`](../specs/2026-08-03-v0.4.1-design.md)

## Governing constraint

Every assertion this release churns is a **hand-written Go string literal or a
live chromedp DOM query**. There is no regeneration mechanism that reaches any
of them (see §5). So the plan sequences narrow, single-concern edits — lint
gate, render-core split, seven partials, viewer CSS, viewer JS + browser tests
— each proven by its own targeted command, ending in a full `make test` /
`make viewer-test` gate. A churned assertion that silently widened the
sanitiser boundary, or that now passes for the wrong reason, cannot slip
through unread.

The #25 relaxation touches **leg 1 only** of `checkMockupGate`. The module
allowlist, the tag/attribute/class allowlist, the `raw_html_reviewed` gate and
`components.MockupHTML`'s layout-blind render gate are all left untouched, and
that non-change is recorded in code and proven by a grep, not left as an
omission (decision C2).

## 1. Lane graph

```
L1 (lint + docs)  ──────────────┐
                                │
L2 (render core) ──┬─→ L3 (partials + render) ──┬─→ L4 (style.css) ──┐
                   │                            │                    │
                   └────────────────────────────┴────────────────────┴─→ L5 (shell.html + viewer-tests) ─→ FINAL GATE
```

| Lane | Owns | Depends on | Model | Effort |
|---|---|---|---|---|
| **L1** | the `raw-html-scope` lint gate, its two proof tests, and the prose that states the old rule | — | **Sonnet** | medium |
| **L2** | `components.go`'s chip extraction + `<details>` wrapper, and the two component test files | — | **Opus** | high |
| **L3** | all seven layout partials, `render.go`'s id-strip re-verification, and the render-level comment tests | L2 | **Opus** | high |
| **L4** | every new/changed CSS rule | L2, L3 | **Opus** | medium |
| **L5** | the viewer JS selectors, the expand-all toolbar, and the chromedp suite | L3, L4 | **Sonnet** | medium |

**Why L3 does not depend on L1.** L3 edits `mockup.html`'s doc comment, which
describes the lint rule L1 relaxes. That is *content* coupling to a decision
already settled (C1/C3), not a build or test edge — no partial compiles against
the lint package, and no render test runs lint. Declaring the edge would
serialise two lanes that can run in parallel. The final gate catches any
mismatch.

**Why `style.css` and `shell.html` are separate lanes.** They were one lane in
the winning outline. Model assignment forces the split: CSS is Opus work,
`shell.html` is Sonnet work, and a lane carries one model.

**The one intended red window.** Three assertions live in files L2 owns
(`components_test.go`, `comments_test.go`) but are satisfied by markup L3 owns
(the seven partials). Rather than split test-file ownership across lanes — which
is how the contention-first outline ended up with L2 both feeding and following
L3 — L2 writes the new expectation and L3 satisfies it. Steps 9-11 name the
three tests, step 11's gate `-skip`s exactly them, and step 14's `-run` is the
exact complement. Outside that window every gate in this plan is a clean pass.

## 5. Golden regeneration

**There is no *golden* regeneration mechanism that reaches any test assertion
this release changes.** One generated artifact *is* regenerated, and it is not
a golden: the two committed sample viewers under `testdata/fixture-*/viewer/`
are rewritten by `dossierx check` itself (`internal/check/check.go:243-252`,
invocation documented at `CONTRIBUTING.md:66`) at **step 24b**. No test reads
them; they exist as demonstration artifacts. Everything below is about test
assertions.

The repo has exactly one golden-regeneration mechanism:

```
go test ./... -regenerate-goldens
```

backed by the `regenerateGoldens` flag at
`internal/render/markdown/markdown_golden_test.go:12` and
`internal/render/markdown/generate-goldens/main.go`. It regenerates **only**
`testdata/markdown-cases` and `testdata/markdown-claim-body-cases` — the
CommonMark renderer's fixtures. It has **zero reach** into the claim-footer,
card-head or comment-chip markup this release touches. Do not run it expecting
it to fix anything here; it will not, and a clean run of it proves nothing
about this work.

Every assertion this release churns is one of:

- a hand-written Go string literal (`strings.Contains` / `strings.Count` /
  exact match) in `components_test.go`, `comments_test.go`,
  `comments_render_test.go`, `raw_html_scope_test.go`,
  `check_parity_test.go`; or
- a live chromedp DOM query in `viewer-tests/`.

**Process: every one is a manual edit, read before commit.** Never
regenerate-and-diff. The whole reason this plan sequences narrow single-concern
steps is that the only reviewer of these diffs is a human reading them.

Test-reach note: `make test` runs `go build ./... && go vet ./... && go test ./...`
and reaches every `internal/...` and `cmd/...` test above, but **does not**
descend into `viewer-tests` (a separate Go module, by design, so chromedp stays
out of the engine's `go.mod`) or `hook-test` (a bash suite, unrelated to this
work). `make viewer-test` is the only way to run the browser suite.
