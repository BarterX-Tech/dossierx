Memo

Why DossierX exists

Documentation does not fail loudly. It fails by staying up, staying readable, and slowly becoming false. DossierX tries to make that failure produce a signal.

The problem

A wiki page, an architecture decision record, a docs/ folder. They all fail the same way. Prose can become wrong without emitting anything a machine notices. No build breaks. No test goes red. The page renders exactly as it did the day it was correct, and people keep reading it and acting on it.

That was survivable while people wrote documentation slowly, by hand, alongside the code it described. It is much less survivable now. An agent can write more documentation in an afternoon than a team reads in a week. The volume went up and the review capacity did not. What gets written stopped being the constraint. What anyone has actually approved is the constraint.

The idea

Stop asking people to trust pages. Give them facts instead. A claim is one reviewable statement, a single fact in YAML, with its dependencies declared. You can lint facts at that grain, cross-check them against each other, and tie them to the code that implements them. You cannot do any of that to a page.

Once a human approves a claim, it locks. After that it cannot change quietly. Edit a locked claim, move a dependency underneath it, or write code that no longer matches it, and DossierX emits a named finding. The finding says which rule fired, which claim it fired on, and which command puts it right.

Two users, two surfaces

An agent cannot operate a tool that answers in English sentences. So the agent gets the CLI. It returns JSON by default, one response envelope per invocation, stable error codes to branch on, and a dry run on everything that writes.

You get a browser. Run dossierx serve, read the claims, comment on any card, resolve the threads you opened. That Resolve click is the approval, and it carries real weight. A claim with an open thread cannot lock.

The gate is narrower than it sounds, and I think that narrowness is the best decision in the tool. Draft claims are the agent's workshop and stay unfrictioned. Friction there would defeat the point. The invariant is only this. Nothing already locked changes without your approval on the record.

DossierX detects, the forge enforces

The lock ledger rides in git, so DossierX can turn a quiet edit into a specific named finding. It cannot make anyone obey that finding. Branch protection with a required CI check does that. The pre-commit hook in front of it gives fast feedback and no authority.

I like this split. A red check here means something concrete enough to act on, and the tool never claims a power it does not have.

Where it came from

DossierX started as internal tooling inside a private production application that silent documentation drift had already burned. The public tool keeps what worked there, the claim schema, the check pipeline, the lock lifecycle, and reads every project-specific structure from one project.config.yaml. Point the same binary at another project's config and it becomes that project's documentation engine.

What is still open

This is the honest part. DossierX is pre-1.0 and its shape has moved every few releases. The command surface has been cut and rebuilt once already, and it may move again. The right unit of review is not settled either. A claim belongs to a module, but the thing a user actually receives cuts across many modules, and the current attempt at that middle layer is young.

Whether any of this generalises is genuinely open. It might be a tool other teams want. It might be one project's answer to one project's problem. I do not know yet, and this page is short because the broader direction is not worth a long one.

The details that have to be correct live where someone can check them against the binary. The README covers what the tool does and how to set it up. The changelog covers what each release changed. The release history lists what has shipped.
